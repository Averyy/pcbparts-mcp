# Amendments to eastern-days-spec.md (after review)

These change the first implementation of `docs/eastern-days-spec.md`. Where they conflict, this file wins.

1. **Place rare events by their own hourly series, not by call volume.** Failures, refusals and held-back lookups cluster in single hours, so spreading them by `hours` puts them on the wrong Eastern day. In `at()` interpolation, weight each field family by its hourly sibling instead of `hours`:
   - `tools.<t>.failed`, and in `reasons.<t>` the failure labels (`service_not_ready`, `not_configured`, `no_pcba_types`, `query_too_complex`, `board_db_failed`, `jlcpcb_waf`, `jlcpcb_unavailable`, `easyeda_failed`, `mouser_failed`, `digikey_failed`, `cse_auth_failed`, `cse_lookup_failed`, `cse_download_http_4xx`, `cse_download_http_5xx`, `cse_download_http`, `cse_download_network`, `cse_download_too_large`, `cse_invalid_zip`, `cse_download_refused`, `lifecycle_lookup_failed`, `exception`, `unexpected_error`): `failed_hours`.
   - `per_ip_refusals.*`: `refused_hours`.
   - `distributor_limits.<d>.held_back.*` and `distributors.<d>.rate_limited`: that distributor's `held_back_hours`.
   - `db_waits.waited` (and `components.waited`): the matching `waited_hours`.
   - Everything else: `hours`.
   When a field has an hourly sibling, its window total must equal the sum of the sibling's entries in the window wherever the sibling is recorded (so the page's totals agree with its hourly charts). A sibling that is `null` for the hours involved falls back to `hours`.
2. **Round once, per window, not inside `at()`.** Keep fractional values through `at()` and subtraction; round the finished window record. For `tools.<t>`, round the outcomes with the largest-remainder method so `ok + similar_only + not_found + bad_request + rate_limited + failed` equals the rounded `calls`; do the same for each `reasons.<t>` against that tool's `not_found + failed`, and for `per_ip_refusals` groups against its `total`.
3. **Approximation per field family.** Replace the single `approx` flag with `approx` (true if anything was interpolated) plus `exact_calls` (true when `hours` covers the whole window, which is almost always). The page states approximation once, in its footer.
4. **The problems baseline uses a nearby snapshot as is.** For the start of the problems window (`problems_since`), a snapshot within 10 minutes after `problems_since` (and before the first fetch that saw the new version, when that is known) is used as the exact baseline value instead of interpolating. Today that is the 1:04 PM EST snapshot (`2026-11-21T18:04:00Z`) for `PROBLEMS_SINCE=2026-11-21T18:00:00Z`. Hourly lists in the problems window still start at the hour containing `problems_since`.
5. **Automatic `problems_since` on a version change:** use the `fetched_at` of the last stored fetch whose `/health` reported the old version (its stats snapshot is the exact baseline), not the start of the hour of the first fetch with the new version. If no fetch with the old version exists, use the first fetch with the new version.
6. **No stub first day.** An Eastern day that starts before the first stored UTC day's 00:00 (the store begins mid-Eastern-day) gets `partial_start: true`; the page leaves it out of ranges and charts. Likewise the payload marks `partial_end` for today (already `complete: false`).
7. **Recompute after rule changes.** Add a `rules_version INTEGER` column to `eastern_days` (start at 2 with these amendments); a persisted day with an older `rules_version` is recomputed when its inputs are still available, else kept as is.
8. **Version start for the header.** Add `version_since` to the payload: `{version, since}` for the version `/health` currently reports, `since` being `problems_since` when `problems_version` matches it, else the first fetch that saw that version.
9. **Daily budgets reset at 7 PM EST.** No backend change; noted so the page says "resets 7 PM" next to Mouser/DigiKey budgets and per-address allowances, which follow the server's day, not the Eastern day.
